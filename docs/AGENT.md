# NexOPS Agent — Operator Reference

This document describes the NexOPS agent: what it does, how it's installed, how it authenticates, and how to manage it on target machines.

---

## What the Agent Does

The NexOPS agent is a **privileged, outbound-only** Go binary that runs on each managed Linux target (Ubuntu/Debian). It:

1. **Polls the control plane** every 30 seconds (configurable) via `POST /api/agent/heartbeat`
2. **Sends telemetry**: CPU, memory, disk, network, load, uptime, kernel, services, package updates
3. **Receives jobs** inline in the heartbeat response (apt update/upgrade, service status, agent self-update)
4. **Executes jobs** as root via systemd-run with timeout enforcement
5. **Reports results** via `POST /api/agent/jobs/:id/result`
6. **Self-updates** on request: verifies the published release and replaces its own binary, then restarts

The agent **never listens on a network port**. All communication is outbound HTTPS to the control plane.

## Installation

### Prerequisites on Target

- Ubuntu 22.04+ or Debian 12+
- Root access (for install)
- `curl`, `sha256sum`, `systemd` (standard on supported distros)
- Outbound HTTPS (port 443) to the control plane URL

### Install Command (Generated by Control Plane)

```bash
curl -fsSLO "$BASE/api/agent/releases/install.sh" \
  && curl -fsSLO "$BASE/api/agent/releases/install.sh.sha256" \
  && sha256sum -c install.sh.sha256 \
  && sudo ENROL_TOKEN=<token> CONTROL_PLANE_URL=<BASE> OS=<ubuntu|debian> bash install.sh \
  && rm -f install.sh install.sh.sha256
```

- `$BASE` = `NEXT_PUBLIC_APP_URL` (pinned by `PUBLIC_ORIGIN` via compose; otherwise the request origin). Must be HTTPS in production.
- `ENROL_TOKEN` = single-use, 15-minute expiry, returned once from `POST /api/targets`
- `OS` = `ubuntu` or `debian` (determines package manager commands)

### What `install.sh` Does

1. Verifies root (`EUID == 0`)
2. Validates `ENROL_TOKEN`, `CONTROL_PLANE_URL`, `OS`
3. Creates system user/group `nexops-agent` (UID/GID allocated dynamically)
4. Downloads `nexops-agent-linux-<arch>` + `.sha256` from `/api/agent/releases/`, verifies checksum
5. Installs binary to `/var/lib/nexops/bin/nexops-agent` (mode 0755, owned `nexops-agent:nexops-agent`)
6. Writes `/etc/nexops/agent.env` (mode 0600, owned `root:nexops-agent`) with:
   ```
   CONTROL_PLANE_URL=https://nexops.example.com
   ENROL_TOKEN=<token>
   OS=UBUNTU
   ```
7. Installs systemd unit `/etc/systemd/system/nexops-agent.service`:
   ```ini
   [Unit]
   Description=NexOPS fleet agent
   After=network-online.target
   Wants=network-online.target

   [Service]
   Type=simple
   User=nexops-agent
   Group=nexops-agent
   EnvironmentFile=/etc/nexops/agent.env
   ExecStart=/var/lib/nexops/bin/nexops-agent
   Restart=always
   RestartSec=5
   TimeoutStopSec=30
   ProtectHome=true
   PrivateTmp=true
   ProtectKernelTunables=true
   ProtectKernelModules=true
   ProtectControlGroups=true
   LockPersonality=true

   [Install]
   WantedBy=multi-user.target
   ```
8. Runs `systemctl daemon-reload && systemctl enable --now nexops-agent`

## Files on Target

| Path | Owner | Mode | Purpose |
|------|-------|------|---------|
| `/var/lib/nexops/bin/nexops-agent` | nexops-agent:nexops-agent | 0755 | Agent binary (service-owned so unprivileged self-update can atomically replace it) |
| `/etc/nexops/agent.env` | root:nexops-agent | 0600 | Static config (CONTROL_PLANE_URL, OS) + initial ENROL_TOKEN |
| `/var/lib/nexops/agent.key` | nexops-agent:nexops-agent | 0600 | Ed25519 private key (generated on first start, **never leaves target**) |
| `/var/lib/nexops/agent.env` | nexops-agent:nexops-agent | 0600 | Runtime credentials (bearer token, written after enrolment) |
| `/var/lib/nexops/` | nexops-agent:nexops-agent | 0750 | Agent data directory |

## Authentication Flow

### 1. First Start (Enrolment)

1. Agent reads `ENROL_TOKEN` from `/etc/nexops/agent.env`
2. Generates Ed25519 keypair → saves private key to `/var/lib/nexops/agent.key`
3. Calls `POST /api/agent/enrol` with token, public key, hostname, OS, arch, version, signature
4. Control plane:
   - Verifies token hash, expiry, not used
   - Verifies signature over raw token bytes
   - Consumes token (`usedAt = now`)
   - Creates `AgentIdentity` with `publicKey`, `credentialHash` (SHA-256 of new bearer credential)
   - Returns `{ agentId, targetId, credential, heartbeatIntervalSec }`
5. Agent writes `credential` to `/var/lib/nexops/agent.env` (mode 0600)
6. Agent **scrubs `ENROL_TOKEN` from `/etc/nexops/agent.env`** (removes the line)

### 2. Ongoing Requests

Every subsequent request (heartbeat, job results) includes:
```
Authorization: Bearer <credential>
```

Control plane hashes the credential and looks up `AgentIdentity` by `credentialHash`.

### 3. Revocation

**Deleting a target in the control plane:**
- Sets `AgentIdentity.credentialHash = NULL`
- Sets `AgentIdentity.revokedAt = now`
- Soft-deletes `Target` (`deletedAt = now`)
- Cancels queued jobs

**Effect on agent:** Next heartbeat returns `401 Unauthorized`. The agent **exits with code 1** and systemd restarts it. The restart loop will continue failing until the target is re-enrolled (new install command).

---

## Credential Rotation

To rotate an agent's credential without deleting the target:

1. In control plane: `DELETE /api/targets/:id` (revokes credential, soft-deletes target)
2. Create new target: `POST /api/targets` → new `installCommand`
3. Re-run install command on target

The old binary remains but will fail auth on next heartbeat. The new install replaces the binary and starts fresh.

## Systemd Management

```bash
# Status
systemctl status nexops-agent

# Logs
journalctl -u nexops-agent -f

# Restart
systemctl restart nexops-agent

# Stop (disable auto-start)
systemctl disable --now nexops-agent

# View environment
systemctl show nexops-agent --property=Environment
```

---

## Uninstall

```bash
# 1. Stop and disable service
systemctl disable --now nexops-agent

# 2. Remove systemd unit
rm -f /etc/systemd/system/nexops-agent.service
systemctl daemon-reload

# 3. Remove binary (also remove legacy copy if upgrading from the old layout)
rm -f /var/lib/nexops/bin/nexops-agent /usr/local/bin/nexops-agent

# 4. Remove config and data
rm -rf /etc/nexops /var/lib/nexops

# 5. Remove user/group (optional)
userdel nexops-agent 2>/dev/null || true
groupdel nexops-agent 2>/dev/null || true
```

## Troubleshooting

| Symptom | Check | Fix |
|---------|-------|-----|
| Agent not starting | `journalctl -u nexops-agent -n 50` | Fix config / network / binary |
| `401 Unauthorized` in logs | Target deleted in control plane | Re-enrol (new install command) |
| `checksum mismatch` on install | Binary changed or corrupted download | Rebuild control plane (`docker compose up -d --build`), re-run install |
| `connection refused` | Wrong `CONTROL_PLANE_URL` or firewall | Verify URL in `/etc/nexops/agent.env`; test `curl <URL>/` |
| High CPU/memory | Job runaway / bug | Check job history in dashboard; restart agent |

## Upgrading the Agent

### Self-update from the dashboard

Agents that run a version with `SELF_UPDATE` support upgrade themselves: run
the **Self-update** job for the target (or a bulk self-update for the whole
fleet) in the dashboard. The agent then

1. downloads `nexops-agent-linux-<arch>` and its `.sha256` sidecar from the
   control plane it is enrolled with,
2. verifies the binary against the sidecar digest,
3. executes the staged binary with `version` (10 s timeout) **before** the
   running binary is touched, refusing the update if it cannot start,
4. replaces `/var/lib/nexops/bin/nexops-agent` atomically and keeps the
   previous build at `/var/lib/nexops/bin/nexops-agent.prev`,
5. reports the job result and then restarts itself (the PID is preserved, so
   systemd keeps tracking the same service).

The agent must be able to write to the directory of its own executable: the
installer places it in `/var/lib/nexops/bin`, owned by `nexops-agent`, so
unprivileged self-update can create a same-directory temp file and atomically
rename it over the running binary. The control-plane TLS origin plus the
SHA-256 sidecar remain the trust anchor; a compromised agent can only replace
its own binary (it already runs arbitrary code as that user).

To roll back a bad update, restore the previous build and restart the agent:

```bash
sudo mv -f /var/lib/nexops/bin/nexops-agent.prev /var/lib/nexops/bin/nexops-agent && sudo systemctl restart nexops-agent
```

> **Bootstrap caveat:** agents installed before the `SELF_UPDATE` job type
> existed reject the job with `unknown job type "SELF_UPDATE"`. Those hosts
> need one manual install re-run before self-update works; all later upgrades
> are then fleet-wide with no SSH. Get the command from **Target page →
> Re-issue install command**, which returns a fresh one-time token and
> invalidates any previous unconsumed tokens for the target. The old
> credential stops working at the moment the new enrolment succeeds.

### Manual upgrade (bootstrap for legacy agents)

An agent that predates `SELF_UPDATE` does not know the job type and fails the
job with `unknown job type` — the first upgrade must be manual. After a
control-plane upgrade:

```bash
# On each target, re-run the install command (fetches new binary, verifies, replaces, restarts)
curl -fsSLO "https://nexops.example.com/api/agent/releases/install.sh" \
  && curl -fsSLO "https://nexops.example.com/api/agent/releases/install.sh.sha256" \
  && sha256sum -c install.sh.sha256 \
  && sudo ENROL_TOKEN=<new-token> CONTROL_PLANE_URL=https://nexops.example.com OS=ubuntu bash install.sh \
  && rm -f install.sh install.sh.sha256
```

Get a new `ENROL_TOKEN` with **Target page → Re-issue install command** — it
returns the full command with a one-time token and invalidates any previous
unconsumed tokens for that target. Creating a new target also works but changes
the target identity.
Once the fleet runs a self-updating agent, later upgrades are a dashboard job.

## Security Notes

- **Private key never leaves target** (`/var/lib/nexops/agent.key`, mode 0600)
- **Bearer credential stored once** (`/var/lib/nexops/agent.env`, mode 0600)
- **Enrolment token scrubbed** after first successful enrolment
- **TLS verification always enabled** (no `-k`/`--insecure` in curl or agent)
- **Systemd hardening**: `NoNewPrivileges`, `ProtectSystem=strict`, minimal capabilities
- **Agent runs as unprivileged user** `nexops-agent` (only the install script runs as root)

## API Endpoints the Agent Uses

| Method | Path | Auth | Purpose |
|--------|------|------|---------|
| `GET` | `/api/agent/releases/install.sh` | None | Install script |
| `GET` | `/api/agent/releases/install.sh.sha256` | None | Install script checksum |
| `GET` | `/api/agent/releases/nexops-agent-linux-<arch>` | None | Agent binary |
| `GET` | `/api/agent/releases/nexops-agent-linux-<arch>.sha256` | None | Binary checksum |
| `POST` | `/api/agent/enrol` | None (token in body) | Initial enrolment |
| `POST` | `/api/agent/heartbeat` | Bearer credential | Telemetry + job dispatch |
| `POST` | `/api/agent/jobs/:id/result` | Bearer credential | Job result submission |

All release endpoints are **public** (no auth) so the install script can fetch them before enrolment.
