# NexOPS Architecture

NexOPS is a self-hosted VM fleet management platform. A Next.js control plane
holds state in PostgreSQL and manages Linux targets through a privileged agent.
This document is the **contract** three parallel workstreams build against.
Anything not specified here is an implementation detail.

```
 Browser ──Clerk──▶ Next.js control plane ──Prisma──▶ PostgreSQL
                          ▲  │
             outbound pull│  │ (agent polls; no inbound ports)
                     Agent (Go) on each target
```

The agent is **outbound-only**. It never listens on a port; it polls the control
plane and receives work in the poll response. This keeps targets reachable
behind NAT/firewalls without opening inbound access.

---

## 1. Enrolment flow

1. An authenticated operator calls `POST /api/targets` (Clerk session) with a
   name, OS family, and optional metadata. The control plane:
   - creates a `Target` with `status = PENDING_ENROLMENT`;
   - creates an `EnrolmentToken` whose plaintext is 32 random bytes encoded as
     base64url. **Only the SHA-256 hash is stored** (`tokenHash`, unique).
   - sets `expiresAt = now + 15 minutes`; the token is **single-use**.
   - writes an `AuditEvent` (`actorType = USER`, `action = "target.create"`).
2. The response is `CreateTargetResponseDto` and contains, once and only once,
   the plaintext `enrolmentToken`, its `expiresAt`, and a ready-to-run
   `installCommand`.
3. The operator runs `installCommand` as root on the target.

### installCommand

```sh
curl -fsSLO "$BASE/api/agent/releases/install.sh" && curl -fsSLO "$BASE/api/agent/releases/install.sh.sha256" && sha256sum -c install.sh.sha256 && sudo ENROL_TOKEN=<token> CONTROL_PLANE_URL=<BASE> OS=<ubuntu|debian> bash install.sh; rm -f install.sh install.sh.sha256
```

`$BASE` is `NEXT_PUBLIC_APP_URL` (pinned by `PUBLIC_ORIGIN` via compose; otherwise the request origin). The script is fetched over TLS, its SHA-256 is
verified against the sibling `.sha256` file **before** execution, and the
temporary files are removed afterwards.

### install.sh (served at `GET /api/agent/releases/install.sh`)

Generated by the backend and served together with its `.sha256` sidecar. It:

1. Requires root (`EUID == 0`, otherwise exit `1` with a clear message).
2. Validates required env: `ENROL_TOKEN`, `CONTROL_PLANE_URL`, `OS`
   (`ubuntu|debian`). Missing/invalid values exit `2` with usage text.
3. Creates the unprivileged system user/group `nexops-agent` (idempotent).
4. Downloads `nexops-agent-linux-<arch>` and its `.sha256` from
   `/api/agent/releases/`, verifies the checksum, and aborts (exit `3`) on
   mismatch.
5. Installs the binary to `/usr/local/bin/nexops-agent` (mode `0755`).
6. Writes `/etc/nexops/agent.env` (mode `0600`, owned `root:nexops-agent`)
   containing `CONTROL_PLANE_URL`, `ENROL_TOKEN`, and `OS`.
7. Installs a systemd unit (`Restart=always`, `User=nexops-agent`,
   `ProtectHome=true`, `PrivateTmp=true`, `ProtectKernel*`,
   `LockPersonality=true`) and runs `systemctl daemon-reload`,
   `enable nexops-agent.service`, `restart nexops-agent.service` (restart,
   not start — `systemctl start` is a no-op on an already-active unit and
   would leave the old process running with the old environment). The unit
   deliberately has **no read-only mount-namespace sandbox** (`ProtectSystem`
   / `ReadWritePaths`): dpkg/apt must write `/usr`, `/etc`, and
   `/var/cache/debconf` during a real upgrade, so a read-only root would break
   the agent's core feature. Privilege is bounded by the unprivileged service
   user plus the audited `/usr/local/libexec/nexops-apt` sudoers helper
   (whitelisted subcommands, no argument injection).
8. Prints the agent's first-start instructions and exits `0`.

TLS certificate verification is **never** disabled in `curl` or the agent.
Any download or network failure exits non-zero with an actionable message.

## 2. Agent authentication

**First start.** The agent generates an Ed25519 keypair; the private key is
written to `/var/lib/nexops/agent.key` with mode `0600` and **never leaves the
target**. It then calls `POST /api/agent/enrol`:

```json
{
  "token": "<ENROL_TOKEN>",
  "publicKey": "<base64 ed25519 public key>",
  "hostname": "vm-01",
  "os": "UBUNTU",
  "arch": "amd64",
  "osVersion": "24.04",
  "agentVersion": "0.1.0",
  "signature": "<base64 ed25519 signature over raw token bytes>"
}
```

The control plane:

1. Looks up the token by `SHA-256(token)`, rejects if missing, expired, or
   already `usedAt`.
2. Verifies `signature` against `publicKey` over the raw token bytes.
3. Consumes the token (`usedAt = now`) inside the same transaction that creates
   the `AgentIdentity` for the target and sets `enrolledAt`, `agentVersion`,
   `publicKey`.
4. Issues a **per-agent bearer credential**: 32 random bytes, returned once;
   only `SHA-256` is persisted (`AgentIdentity.credentialHash`) with
   `credentialIssuedAt`.
5. Responds:

```json
{ "agentId": "...", "targetId": "...", "credential": "<plaintext>", "heartbeatIntervalSec": 30 }
```

The agent stores the credential (`/var/lib/nexops/agent.env`, mode `0600`),
then **scrubs `ENROL_TOKEN`** from `/etc/nexops/agent.env`.

**Ongoing auth.** Every `/api/agent/*` request except the release endpoints
sends `Authorization: Bearer <credential>`. The control plane hashes it and
resolves it via the unique `credentialHash`, rejecting unknown/revoked
credentials.

**Revocation.** Deleting a target nullifies `credentialHash`, sets `revokedAt`,
soft-deletes, and cancels queued jobs (see API below). A revoked credential no
longer resolves.

## 3. Agent protocol (outbound-only pull)

### `POST /api/agent/heartbeat`

Batched telemetry plus dispatch. Body (Zod-validated, see `HeartbeatRequest`
in `src/lib/types.ts`):

```json
{
  "capturedAt": "2026-01-01T12:00:00Z",
  "cpuPct": 12.5,
  "cores": 4,
  "load1": 0.4, "load5": 0.3, "load15": 0.2,
  "memTotalBytes": 8589934592,
  "memUsedBytes": 3221225472,
  "memAvailableBytes": 5368709120,
  "swapUsedBytes": 0,
  "disks": [{ "mount": "/", "fsType": "ext4", "totalBytes": 100, "usedBytes": 40, "inodesTotal": 1000, "inodesUsed": 100 }],
  "net": [{ "name": "eth0", "rxBytes": 1, "txBytes": 2, "rxRateBps": 0.0, "txRateBps": 0.0 }],
  "uptimeSec": 123456,
  "bootTime": "2025-12-01T00:00:00Z",
  "kernel": "6.8.0-45-generic",
  "hostname": "vm-01",
  "agentVersion": "0.1.0",
  "services": [{ "name": "nginx", "state": "active" }],
  "pkgUpdates": { "availableCount": 3, "rebootRequired": false },
  "activeJobIds": ["job_01H..."]
}
```

`memAvailableBytes` **must** come from Linux `/proc/meminfo` `MemAvailable`
(not `MemFree`).

The agent heartbeats **immediately on start**, before the first interval, so a
freshly enrolled target reaches `ONLINE` without waiting a full tick.
Collection is bounded (~10s); if a collector wedges, the beat proceeds with
partial data and missing metrics are sent as `null` rather than delaying the
beat past the 90s liveness window. `pkgUpdates` is refreshed in the background
at most once per 10 minutes, so it may be `null` on a given beat — `null`
honestly means "not measured within the last TTL".

`lastTelemetryAt` only advances for heartbeats carrying usable telemetry
(`memTotalBytes > 0`, which the agent reports only when it actually sampled
`/proc/meminfo`); a heartbeat without usable telemetry is connectivity-only.

`activeJobIds` (optional) lists the jobs the agent is currently running **or**
has accepted but not yet finished. The agent keeps heartbeating on its ticker
while a long job executes, so this is how the control plane learns which jobs
are still live on the host.

Server side: persists a `TelemetrySnapshot`, sets `Target.lastTelemetryAt` and
`lastHeartbeatAt`, promotes `PENDING_ENROLMENT → ONLINE` on the first valid
heartbeat, and returns pending jobs to run inline:

```json
{
  "jobs": [ /* JobDto[] */ ],
  "cancelledJobIds": ["job_01H..."]
}
```

Jobs dispatched this way move to `DISPATCHED`. `cancelledJobIds` (optional) is
the intersection of the request's `activeJobIds` with jobs that are now
`CANCELLED`; the server computes it statelessly on every beat. The agent
cancels the matching running job (killing its process group) and drops any
matching queued-but-unstarted job without executing it. Both fields are
optional and backward-compatible: an older agent omits `activeJobIds` and
ignores `cancelledJobIds`; an older control plane omits `cancelledJobIds`.

### Cancellation

`POST /api/jobs/:id/cancel` moves a `QUEUED`, `DISPATCHED` or `RUNNING` job to
`CANCELLED` immediately (audited as `job.cancel`) and returns the updated
`JobDto`. Terminal jobs (`SUCCEEDED`/`FAILED`/`CANCELLED`/`TIMED_OUT`) are
rejected with `409`. For a job already on a host, the control plane does not
signal the agent directly — the next heartbeat carries the job in
`activeJobIds` and the response returns it in `cancelledJobIds`. The agent then
kills the process group and reports a `CANCELLED` result; because the job is
already terminal, that result POST is an idempotent no-op (see below). A job
cancelled between dispatch and the agent starting it is skipped entirely.

### Bulk dispatch

`POST /api/jobs/bulk` creates one job per target in a single transaction.

```json
{ "type": "APT_UPGRADE", "targetIds": ["clx…", "clx…"] }
```

`type` is either `APT_UPGRADE` or `SELF_UPDATE`. `targetIds` is optional: when
omitted, the job targets every eligible target of the fleet. Supplied ids are
de-duplicated, validated as CUIDs and capped at 500 per request.

A target is eligible when its derived status is `ONLINE` or `DEGRADED`.
Everything else is skipped with a reason: `offline`, `pending_enrolment`,
`enrolment_failed`, `maintenance`, `not_found` (unknown or soft-deleted
target). The response is always `200`:

```json
{ "created": 2, "skipped": [{ "targetId": "clx…", "reason": "offline" }] }
```

`created: 0` is a valid outcome (nothing was eligible), not an error. The
request is audited once as `jobs.bulkCreate` with the created target ids.

### Retry

`POST /api/jobs/:id/retry` re-queues a failed job. The body is empty.

- The original job must be `FAILED` or `TIMED_OUT`; anything else is rejected
  with `409` and code `job_not_retryable`.
- A different job of the same type for the same target that is still
  `QUEUED`, `DISPATCHED` or `RUNNING` is rejected with `409` and code
  `job_already_active`.

On success a new `QUEUED` job is created with the same `targetId`, `type`,
`params` and `timeoutSec` as the original, and the endpoint returns
`{ "job": JobDto }`. The action is audited as `job.retry` with the original and
new job ids.

### `POST /api/agent/jobs/:id/result`

```json
{
  "status": "SUCCEEDED",
  "exitCode": 0,
  "stdoutTail": "…last ~8KB…",
  "stderrTail": "",
  "startedAt": "2026-01-01T12:00:01Z",
  "finishedAt": "2026-01-01T12:00:09Z"
}
```

**Idempotent**: replaying a result for an already-terminal job is a no-op
(`200`) and does not overwrite the first terminal state. This is what makes a
cancelled job safe: the operator's `CANCELLED` write wins, and the agent's
later `CANCELLED` result (posted after it kills the process group) is ignored.

**Execution policy.** Each job carries `timeoutSec` (default `600`). The agent
kills the process group on timeout and reports `TIMED_OUT`; the control plane
also transitions a job to `TIMED_OUT` if `startedAt + timeoutSec` elapses while
still non-terminal. The accepted result statuses are `SUCCEEDED`, `FAILED`,
`TIMED_OUT` and `CANCELLED`.

**Job types.** `JobType` is a closed enum; the agent hard-maps each type to an
explicit argv vector (never a shell string). Apt maintenance runs through the
audited `/usr/local/libexec/nexops-apt` sudoers helper on hosts, or a direct
`apt-get` fallback in dev/containers.

| `JobType` | Command | Purpose |
| --- | --- | --- |
| `APT_UPDATE` | `apt-get update -y` | Refresh the APT package index. |
| `APT_UPGRADE` | `DEBIAN_FRONTEND=noninteractive apt-get upgrade -y` | Install available upgrades. |
| `APT_FIX_BROKEN` | `DEBIAN_FRONTEND=noninteractive apt-get -f install -y` | Repair a half-configured dpkg state (recovery path). |
| `CHECK_UPDATES` | `apt-get -s upgrade` | Report how many updates are available. |
| `SERVICE_STATUS` | `systemctl status <service> --no-pager -l` | Report a watched unit's state. |
| `SELF_UPDATE` | *(in-process, no shell)* | Replace the running agent binary with the published release. |

### Agent self-update

`SELF_UPDATE` is the only job type that is not a subprocess. The agent:

1. downloads `nexops-agent-linux-<arch>` and its `.sha256` sidecar from
   `GET /api/agent/releases/:file` on the control plane it is already
   enrolled with (same origin as `install.sh` — the agent can never be
   pointed at another host);
2. verifies the binary against the sidecar digest (constant-time compare);
   a mismatch fails the job and nothing is written;
3. writes the verified binary to a temporary file in the same directory,
   `fsync`s it and renames it over the running binary (atomic swap — the old
   binary survives any failure);
4. **reports the job result first** and only then `exec`s the new binary, so
   the control plane never sees a `RUNNING` job whose process was replaced
   mid-flight. The PID is preserved, so systemd keeps tracking the same
   service.

If the running binary already matches the published digest, the job succeeds
with `already up to date (<version>)` and no restart happens.

**Requirements.** The agent process must be able to write to the directory of
its own executable (`/usr/local/bin` in the shipped unit). The shipped unit
runs unprivileged as `nexops-agent` and that directory is root-owned, so
self-update is disabled until the operator grants the agent write access to
it (or installs the agent in a directory it owns) — see `docs/AGENT.md`. A
failed install leaves the running binary untouched and reports an actionable
message. A failed `exec` does not roll back the installation: the new binary
stays installed and activates on the next start.

**Bootstrap caveat.** An agent that predates `SELF_UPDATE` does not know the
job type and fails it with `unknown job type`. The first upgrade of an
existing fleet must therefore use the manual install command from the host
page; every later agent version upgrades itself from the dashboard.

## 4. Status derivation

`Target.status` is **derived**, not manually set, except `MAINTENANCE` which is
a display overlay.

| Condition | Status |
| --- | --- |
| Never had a valid heartbeat | `PENDING_ENROLMENT` |
| Enrolment token expired unused (and never online) | `ENROLMENT_FAILED` |
| `now - lastHeartbeatAt <= 90s` **and** `now - lastTelemetryAt <= 5min` | `ONLINE` |
| `now - lastHeartbeatAt <= 90s` **and** `now - lastTelemetryAt > 5min` | `DEGRADED` |
| `now - lastHeartbeatAt > 90s` | `OFFLINE` |
| Soft-deleted | `REMOVED` |
| A job is `RUNNING` for the target | `MAINTENANCE` (display precedence) |

`MAINTENANCE` is computed at read time and takes precedence over the stored
status for display only. Freshness thresholds are fixed constants for now.

Connectivity (`lastHeartbeatAt`) and telemetry freshness (`lastTelemetryAt`)
are independent, so a connected target whose collection keeps failing is
`DEGRADED` with a `NO_TELEMETRY` warning rather than `ONLINE`.

## 5. Full API surface

All request/response bodies are Zod-validated against the DTOs in
`src/lib/types.ts`. All timestamps are ISO-8601. Byte counts are JSON numbers
(BigInt converted at the boundary).

| Method | Path | Contract |
| --- | --- | --- |
| `GET` | `/api/targets` | Query `q`, `status`, `label`, `sort`, `page`, `pageSize`. Server-side filter/sort/paginate → `Paginated<TargetDto>`. |
| `POST` | `/api/targets` | Body `{ name, os, hostnameOverride?, labels? }` → `CreateTargetResponseDto`. |
| `GET` | `/api/targets/[id]` | `TargetDto`. |
| `PATCH` | `/api/targets/[id]` | Body `{ name?, hostnameOverride?, labels? }` → `TargetDto`. Audited. |
| `DELETE` | `/api/targets/[id]` | Revokes credential (`credentialHash=null`, `revokedAt=now`), cancels `QUEUED` jobs, sets `deletedAt`. Audited. |
| `GET` | `/api/targets/[id]/telemetry` | Query `range=1h\|6h\|24h\|7d` → `TelemetrySeriesDto` (downsampled aggregates). |
| `GET` | `/api/targets/[id]/jobs` | `Paginated<JobDto>`. |
| `GET` | `/api/jobs` | Query `status`, `targetId`, `page` → `Paginated<JobDto>`. |
| `GET` | `/api/jobs/[id]` | `JobDto`. |
| `POST` | `/api/jobs/[id]/cancel` | Cancels a non-terminal job → `JobDto`. Audited. |

### Agent (public matcher; bearer credential enforced in-handler)

| Method | Path | Contract |
| --- | --- | --- |
| `POST` | `/api/agent/enrol` | `AgentEnrolRequest` → `AgentEnrolResponse`. |
| `POST` | `/api/agent/heartbeat` | `HeartbeatRequest` → `HeartbeatResponse`. |

### Rate limiting

In-memory token bucket (no Redis) keyed by target identity / client IP on
`/api/agent/enrol` and `/api/agent/heartbeat`. Buckets are per-process; a
`429` includes `Retry-After`.

## 6. Security

- **Zod** validation on every request body and query.
- **Clerk `auth()`** is called server-side in every protected route; the
  middleware matcher only decides what requires a session.
- Agent requests resolve a target via **credential-hash lookup**; plaintext
  credentials and private keys are never stored server-side.
- **No secrets reach the client.** Credentials and tokens are returned once and
  never included in read DTOs.
- Telemetry **never** contains environment variables, secrets, or file
  contents — only metrics and service *states*.
- **Every mutation writes an `AuditEvent`.** Reads do not.
- Prisma queries are parameterized by default; no string-interpolated SQL.

---

## 7. Retention

- `TELEMETRY_RETENTION_DAYS` (default `30`) bounds `TelemetrySnapshot` age.
- Cleanup runs from `src/instrumentation.ts` on a `setInterval`, guarded by a
  `globalThis` singleton so dev hot reloads cannot stack timers.
- Used `EnrolmentToken` rows older than **7 days** are pruned in the same sweep.

## 8. Parallel work map

Ownership is by directory. Do not edit another stream's files without
coordinating; if a dependency is genuinely required, add it and note it in the
commit message.

| Stream | Owns |
| --- | --- |
| **backend** | `src/app/api/**`, `src/lib/server/**` |
| **frontend** | `src/app/(dashboard)/**`, `src/components/**` (may extend `src/components/ui`) |
| **agent** | `agent/**` (Go) |
| **devops** | `Dockerfile`, `docker-compose.yml`, `docs/**`, `Makefile` |

**Shared, stable (foundation):**

- `src/lib/types.ts` — wire DTOs (source of truth for the contract).
- `src/lib/format.ts` — **DONE**, do not edit.
- `src/components/ui/**` — primitives; extend, don't fork.
- `prisma/schema.prisma` — dataset contract.
- `package.json` — check before editing; add deps deliberately and note them.

## 9. Byte handling

Prisma models use `BigInt` for byte/inode counters. The **API boundary**
converts to `number` for JSON; use `Number(value)` when within
`Number.MAX_SAFE_INTEGER`, otherwise reject or serialise as a string. DTOs
declare byte fields as `number`.
